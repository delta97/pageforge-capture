# PageForge Capture — Independent Max Width/Height + Interactive Crop

## Context

PageForge Capture splits a stitched full-page screenshot into multiple image "parts" using two settings: `maxMegapixelsPerPart` and `maxPartDimension` (a single cap applied to both width and height). In practice, pages often have very different width vs. height constraints (e.g. a fixed-width article vs. an arbitrarily tall page), so one shared dimension cap is unnecessarily blunt. The user wants independent `maxPartWidth`/`maxPartHeight` controls so each axis can be tuned separately, with the existing megapixel budget and splitting logic still applying intelligently on top.

Separately, there's currently no way to trim unwanted content (e.g. a repeated header/banner, blank margins, or content the user doesn't want) out of a capture — the full captured page is always what gets split and exported. The user wants an interactive crop tool on the result page: after the page is stitched, select a region of the whole page visually, and have everything downstream (part-splitting, download, copy, PDF export) operate on just that region.

Both features live entirely in the existing vanilla-JS/no-build-step architecture — no new dependencies.

## Approach

### 1. Replace `maxPartDimension` with independent `maxPartWidth` / `maxPartHeight`

- **`background.js`**: In `DEFAULTS` (lines 3-17), remove `maxPartDimension: 16384` and add `maxPartWidth: 16384, maxPartHeight: 16384`. Add a one-time migration that runs *before* the existing default-merge in `chrome.runtime.onInstalled` (lines 19-23), since `chrome.storage.sync.get(DEFAULTS)` would otherwise silently synthesize the new keys from defaults before a legacy value could be migrated:

  ```js
  chrome.runtime.onInstalled.addListener(async () => {
    await migrateMaxPartDimension();
    const current = await chrome.storage.sync.get(DEFAULTS);
    await chrome.storage.sync.set(current);
    cleanupOldSessions().catch(() => {});
  });

  async function migrateMaxPartDimension() {
    const raw = await chrome.storage.sync.get(['maxPartDimension', 'maxPartWidth', 'maxPartHeight']);
    if (raw.maxPartDimension === undefined) return;
    const patch = {};
    if (raw.maxPartWidth === undefined) patch.maxPartWidth = raw.maxPartDimension;
    if (raw.maxPartHeight === undefined) patch.maxPartHeight = raw.maxPartDimension;
    if (Object.keys(patch).length) await chrome.storage.sync.set(patch);
    await chrome.storage.sync.remove('maxPartDimension');
  }
  ```

  Idempotent: after the first run, `maxPartDimension` no longer exists in storage, so future `onInstalled` firings (extension updates) short-circuit immediately.

- **`options.js`**: Mirror the same `DEFAULTS` change. In `save()` (lines 43-58), replace the single clamp (line 54) with two:
  ```js
  values.maxPartWidth = clamp(values.maxPartWidth || 16384, 512, 32767);
  values.maxPartHeight = clamp(values.maxPartHeight || 16384, 512, 32767);
  ```
  (512 floor chosen over a lower value to avoid pathological part-count explosions on long pages; matches the existing settings-page pattern of `populate()`/`save()` driven generically by `Object.keys(DEFAULTS)`.)

- **`options.html`**: Replace the "Max dimension per image part" row (lines 54-57) with two rows, `id="maxPartWidth"` and `id="maxPartHeight"`, `min="512" max="32767" step="256"`.

- **`result.js`**: In `calculateOutput()` (lines 102-123), replace the shared `maxDim` with independent caps:
  ```js
  const maxWidth = Math.max(512, Number(settings.maxPartWidth) || 16384);
  const maxHeight = Math.max(512, Number(settings.maxPartHeight) || 16384);
  let partWidth = Math.min(bounds.width, maxWidth);
  let partHeight = Math.min(bounds.height, maxHeight, Math.max(1, Math.floor(maxPixels / partWidth)));
  ```
  The megapixel budget still only shrinks height (unchanged behavior/priority), now against independently-capped width/height instead of one shared cap. (`bounds` here comes from the crop feature below — see combined function in section 2.)

### 2. Interactive crop on the final stitched image

Cropping determines the region that gets split into parts, so it must be resolved before `calculateOutput()` tiles the page. Add an optional `cropRect` parameter that produces a `bounds` rect (defaults to the full page), and tile parts over `bounds` instead of the full page:

```js
function calculateOutput(records, meta, settings, cropRect = null) {
  const first = records[0];
  const scaleX = first.bitmap.width / first.browserViewportWidth;
  const scaleY = first.bitmap.height / first.browserViewportHeight;
  const width = Math.max(1, Math.round(meta.contentWidth * scaleX));
  const height = Math.max(1, Math.round(meta.contentHeight * scaleY));
  const bounds = clampCropRect(cropRect, width, height);

  const maxPixels = Math.max(4, Number(settings.maxMegapixelsPerPart) || 30) * 1_000_000;
  const maxWidth = Math.max(512, Number(settings.maxPartWidth) || 16384);
  const maxHeight = Math.max(512, Number(settings.maxPartHeight) || 16384);
  let partWidth = Math.min(bounds.width, maxWidth);
  let partHeight = Math.min(bounds.height, maxHeight, Math.max(1, Math.floor(maxPixels / partWidth)));
  if (partHeight < 1) partHeight = 1;

  const parts = [];
  for (let y = bounds.y; y < bounds.y + bounds.height; y += partHeight) {
    for (let x = bounds.x; x < bounds.x + bounds.width; x += partWidth) {
      parts.push({
        x, y,
        width: Math.min(partWidth, bounds.x + bounds.width - x),
        height: Math.min(partHeight, bounds.y + bounds.height - y)
      });
    }
  }
  return { width, height, scaleX, scaleY, parts, bounds };
}

function clampCropRect(rect, fullWidth, fullHeight) {
  if (!rect) return { x: 0, y: 0, width: fullWidth, height: fullHeight };
  const x = clamp(Math.round(rect.x), 0, fullWidth - 1);
  const y = clamp(Math.round(rect.y), 0, fullHeight - 1);
  return {
    x, y,
    width: clamp(Math.round(rect.width), 1, fullWidth - x),
    height: clamp(Math.round(rect.height), 1, fullHeight - y)
  };
}
```

`width`/`height` keep meaning "full uncropped page" (needed for the crop tool's own preview); `bounds` is the new "currently exported region." Parts stay in absolute output-space coordinates, so tile-drawing math in `renderRegion` needs no coordinate remapping — only its clipping rect needs to become parameterized:

```js
async function renderRegion(region, renderScale = 1, clipBounds = output.bounds) {
  // ...unchanged...
  const intersection = intersect(
    { x: tileX, y: tileY, width: tileW, height: tileH },
    region,
    clipBounds   // was: { x: 0, y: 0, width: output.width, height: output.height }
  );
  // ...unchanged...
}
```

Because it's a default parameter evaluated per-call, `renderParts()`, `downloadParts()`, and `copyCapture()` need zero changes — they get correct crop clipping for free. `exportPdf()` needs explicit updates since it builds its own regions directly rather than going through `output.parts`:

- Line 207 (`showViewer` dimensionSummary): use `output.bounds.width`/`.height` instead of `output.width`/`.height`, so the displayed size matches what's actually being exported (`partSummary` right next to it already reflects `output.parts.length`).
- Line 263 (`exportPdf` continuous-page aspect ratio): `output.bounds.height / output.bounds.width`.
- Lines 267-269 (`exportPdf` continuous-page render): base `targetPixelWidth`/`renderScale` off `output.bounds.width`, and render `output.bounds` (not `{x:0,y:0,...}`) — necessary once crop origin can be nonzero, otherwise it would silently export the page's top-left corner instead of the crop.
- Lines 275-280 (`exportPdf` per-page loop): base `pageRegionHeight`/`targetPixelWidth`/`renderScale` off `output.bounds.width`; loop `y` from `output.bounds.y` to `output.bounds.y + output.bounds.height`; region `x` becomes `output.bounds.x` (not `0`).

**UI**: Add a "Crop" button to the toolbar (`result.html`, next to Copy/PDF/Download), enabled at the same point as the others. Add a `<dialog id="cropDialog">` (styled like the existing `#pdfDialog` but sized `min(96vw,1300px) × min(92vh,900px)`, flex-column layout so header/footer stay visible while only the image stage scrolls) containing:
- A scrollable stage (reuse the `.image-stage` checkerboard background pattern from `result.css:75-84`) showing a `<canvas>` preview of the **whole uncropped page** rendered via `renderRegion({x:0,y:0,width:output.width,height:output.height}, previewScale, {x:0,y:0,width:output.width,height:output.height})`, where `previewScale = Math.min(1, 1100/output.width, 3200/output.height)` — capping both dimensions (not just width) keeps the preview canvas bounded even for extremely tall pages.
- A single absolutely-positioned selection rectangle over the preview, with 8 resize handles (n/s/e/w/ne/nw/se/sw) plus drag-to-move-from-inside and drag-to-create-from-empty-stage-area. Implemented as real overlaid DOM elements so pointer events can be dispatched by `e.target` (handle vs. selection vs. empty stage) instead of manual hit-testing — full pointerdown/pointermove/pointerup algorithm, coordinate handling (client px → preview-canvas-local px, cached stage `getBoundingClientRect()` per-gesture), and per-handle resize math (`applyResize` using `handle.includes('n'|'s'|'e'|'w')`) as detailed in the design pass; minimum selection size = `max(16, 32 * previewScale)` preview px (≈32 real px floor).
- The dim-outside-selection effect via a single `box-shadow: 0 0 0 9999px rgba(15,23,42,.55)` on the selection element (no extra overlay divs needed, and clicks in the dimmed area correctly fall through to start a new selection).
- Footer buttons: **Reset** (sets the in-dialog draft selection back to full-page bounds — does not touch `output` until Apply), **Cancel** (plain `method="dialog"` submit button, same pattern as `#pdfDialog`'s Cancel — needs no JS since nothing is mutated until Apply), **Apply Crop** (converts the draft selection from preview px back to full-res px by dividing by `previewScale`, clamps, then re-runs `output = calculateOutput(decodedTiles, session.meta, session.settings || {}, newCrop)`, `await renderParts()`, `showViewer()`, and updates toolbar button disabled-state — extract the existing inline enable logic from `init()` lines 81-83 into a shared `updateToolbarState()` function so both `init()` and Apply use it, e.g. so Copy re-enables automatically when a crop reduces the part count to 1).
- On dialog open, initialize the draft selection from the *current* `output.bounds` (converted to preview px) so re-opening the tool shows the previously applied crop, not a reset state.

Crop state lives only in memory for the page's lifetime (module-level `output.bounds`) — not persisted to `chrome.storage` or IndexedDB, since `result.html` is regenerated fresh per capture session and this keeps the feature simple. Note: `autoDownload` (if enabled) still fires immediately after the initial uncropped render, before the user has a chance to crop — cropping is an explicit manual action performed afterward; the user would need to click Download again post-crop. This is an acceptable, low-friction tradeoff and needs no special-casing.
