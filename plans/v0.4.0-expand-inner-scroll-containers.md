# Full-Page Capture — Stop Discarding the Page for Inner Scrollers

## Context

Today, `detectInnerScroller` (on by default) finds the single "best"
independently-scrolling element on the page and, if it's dominant enough,
**replaces the entire capture target** with it (`content.js` `chooseScrollTarget`
→ `state.target`/`state.targetType = 'inner'` in `prepare()`). Once that
happens, every downstream measurement — `contentWidth/Height`,
`captureViewportWidth/Height`, and every tile's `captureRect` — is scoped
exclusively to that one element's own box. Headers, sidebars, footers, and
any other page chrome outside that box are never captured at all, not
partially — they simply fall outside the single rectangle re-screenshotted
for every tile. Confirmed via `result.js`'s compositor (`renderRegion`,
`calculateOutput`): it places tiles using a single flat coordinate space, so
this "hijack" behavior isn't a rendering bug, it's the intended (but wrong
for this use case) consequence of the target-replacement design.

The user wants: capture the **whole site** (sidebars, headers, everything)
like a normal full-page capture always has, but **also** make sure a main
content pane's (or any other significant panel's) internal scroll gets fully
exhausted rather than showing only its first screen.

**Chosen approach** (confirmed with the user, avoiding a much riskier
multi-layer-tiling rewrite of `background.js`/`result.js`): never replace the
capture target — always scroll the real document, exactly as today's
non-inner-scroller capture already does. Before that capture begins,
temporarily CSS-expand every qualifying independently vertically-scrolling
container so its full content joins the normal page flow. The existing,
well-tested document-mode scroll/tile/composite pipeline then sweeps it up
automatically, with zero changes to `background.js` or `result.js`.

Confirmed with the user:
- **Expand every qualifying region**, not just a single dominant one (e.g. a
  scrollable sidebar nav *and* a scrollable main content pane both expand).
- **Only vertical overflow is expanded.** Horizontal-only scroll containers
  (card carousels/filmstrips) are left alone — expanding those to full width
  would visually break the page layout in the capture.

## Approach

All changes are in `content.js`, plus a settings-copy update in
`options.html` (and an optional `options.css` touch-up). `background.js`,
`result.js`, `options.js`, and `manifest.json` need no changes — confirmed
none of them reference `targetType`, `chooseScrollTarget`, or otherwise
depend on the inner-target code path.

### 1. `content.js` — replace `chooseScrollTarget` with a two-pass find-then-expand

**Delete** `chooseScrollTarget()` (content.js:223-264) entirely.

**Add** a read-only candidate scan, `findExpandableScrollContainers()`:
```js
function findExpandableScrollContainers() {
  const candidates = [];
  const all = document.querySelectorAll('body *');
  const limit = Math.min(all.length, 7000);
  const viewportHeight = window.innerHeight;

  for (let i = 0; i < limit; i += 1) {
    const el = all[i];
    if (!(el instanceof HTMLElement)) continue;
    if (el.clientHeight < viewportHeight * 0.35) continue;
    if (el.scrollHeight <= el.clientHeight + 80) continue;

    const cs = getComputedStyle(el);
    if (cs.visibility === 'hidden') continue;
    if (!['auto', 'scroll', 'overlay'].includes(cs.overflowY)) continue;

    candidates.push({ el, targetHeight: el.scrollHeight });
  }
  return candidates;
}
```
Key differences from today's heuristic: drops the `clientWidth` size gate (a
narrow, full-height sidebar column must still qualify), checks `overflow-y`
only — never `overflow-x` — which is what naturally excludes horizontal
carousels, and drops the "currently visible in the initial viewport" gate,
since this now runs once as a whole-page pre-pass rather than a
"pick the current best target" decision — a scroller further down an
already-tall page should still get expanded. `scrollHeight` is snapshotted
into `targetHeight` during this same read-only pass, before any mutation.

**Add** expand/restore helpers, mirroring the existing
`collectPositionedElements`/`applyPositionedElementRules`/
`restoreElementVisibility` pattern (content.js:266-320):
```js
function saveInlineProp(el, prop) {
  return {
    had: el.style.getPropertyValue(prop) !== '',
    value: el.style.getPropertyValue(prop),
    priority: el.style.getPropertyPriority(prop)
  };
}
function restoreInlineProp(el, prop, saved) {
  if (saved.had) el.style.setProperty(prop, saved.value, saved.priority);
  else el.style.removeProperty(prop);
}

function expandScrollableRegions() {
  const expanded = [];
  for (const { el, targetHeight } of findExpandableScrollContainers()) {
    expanded.push({
      el,
      transition: saveInlineProp(el, 'transition'),
      flex: saveInlineProp(el, 'flex'),
      maxHeight: saveInlineProp(el, 'max-height'),
      height: saveInlineProp(el, 'height'),
      overflowY: saveInlineProp(el, 'overflow-y')
    });
    el.style.setProperty('transition', 'none', 'important');
    el.style.setProperty('flex', 'none', 'important');
    el.style.setProperty('max-height', 'none', 'important');
    el.style.setProperty('height', `${targetHeight}px`, 'important');
    el.style.setProperty('overflow-y', 'visible', 'important');
  }
  return expanded;
}

function restoreScrollableRegions(list) {
  for (const item of list) {
    restoreInlineProp(item.el, 'transition', item.transition);
    restoreInlineProp(item.el, 'flex', item.flex);
    restoreInlineProp(item.el, 'max-height', item.maxHeight);
    restoreInlineProp(item.el, 'height', item.height);
    restoreInlineProp(item.el, 'overflow-y', item.overflowY);
  }
}
```
Five properties are overridden per candidate, all with `!important` (since
real constrained-height panels are usually driven by stylesheet rules, not
inline styles):
- `transition: none` — prevents an author CSS transition on `height` from
  animating the box's growth mid-capture (would otherwise produce an
  inconsistent layout across tiles). Applied unconditionally, regardless of
  the `pauseAnimations` setting.
- `flex: none` — neutralizes `flex-grow`/`flex-shrink`/`flex-basis` so a
  flex-column child's explicit basis doesn't override our explicit height,
  and `flex-shrink` can't re-collapse the box.
- `max-height: none` — removes any cap that would clamp our explicit height.
- `height: <scrollHeight>px` — grows the box's real layout footprint (not
  just visual overflow) so later siblings get pushed down and the
  document's own scrollHeight grows correctly. An explicit pixel value
  (snapshotted in pass 1) is used rather than `height:auto`, which
  interacts unpredictably with flex/grid stretch algorithms.
- `overflow-y: visible` — belt-and-suspenders against residual clipping.

Add `expanded: []` to the top-level `state` object (content.js:5-15).

**Reorder `prepare()`** (content.js:45-99) so expansion happens, and layout
settles, before `contentHeight` is measured and before fixed/sticky
elements are discovered:
1. Restore old session if any (unchanged).
2. Set `sessionId`/`settings` (unchanged).
3. Hardcode `state.target = document.scrollingElement || document.documentElement;` and `state.targetType = 'document';` — replaces the `chooseScrollTarget()` call and the `targetType` ternary at line 51.
4. Build a simplified `state.original` (see removals below).
5. `root.style.scrollBehavior = 'auto'; body.style.scrollBehavior = 'auto';` — drop the separate `state.target.style.scrollBehavior` write (target is root now, so it'd be redundant).
6. `installCaptureStyles()` — unchanged position, still before expansion.
7. **New**: `state.expanded = expandScrollableRegions();`
8. `collectPositionedElements()` — now runs after expansion, scanning the final (expanded) layout as intended.
9. `window.scrollTo({left:0, top:0, behavior:'auto'})` — drop the `targetType` branch, always this call.
10. `await settle();` — now also covers layout settling from the height/overflow mutations.
11. `getMetrics()` — always measures the document, now correctly including expanded content.

**Simplify now-dead `'inner'` branches** (full removal, per the project's
preference for deleting unused code rather than leaving it half-alive):
- `getMetrics()` (content.js:183-221): delete the `targetType` conditional and the `'inner'` branch (lines 208-220); keep only the document-mode body.
- `scrollToPosition()` (content.js:101-130): delete the `if/else` at lines 108-112 (always `window.scrollTo`) and the ternaries at lines 119-120 (always `window.scrollX/Y`).
- `restore()` (content.js:138-181): delete the `data-pageforge-scroll-target` marker block (lines 160-163) and the target-specific `scrollBehavior`/`scrollbarWidth` restore lines (157-159); delete the `if/else` at lines 165-169 (always restore via `window.scrollTo`). Add `restoreScrollableRegions(state.expanded || []); state.expanded = [];` alongside the existing `restoreElementVisibility(true)` call, and add `state.expanded = []` to the final state-reset block.
- `state.original` construction (lines 55-67): drop `targetX`/`targetY` (now duplicates of `windowX`/`windowY`), `targetScrollBehavior`, `targetScrollbarWidth`, `targetMarker`.
- `installCaptureStyles()` (content.js:322-340): delete the `[data-pageforge-scroll-target="true"]::-webkit-scrollbar` selector and the `state.target.style.scrollbarWidth` line — both existed only for the hijacked-inner-target scrollbar.
- Drop `targetType` from `state` and from the `prepare()` response payload — confirmed nothing in `background.js` reads `prep.targetType`.
- Keep `state.target` as a stored field (set once in `prepare()`) since `scrollToPosition()`/`restore()` already reference it — minimizes diff there.

Replace line 25:
```html
<label class="toggle"><input id="detectInnerScroller" type="checkbox"><span>Auto-detect dominant inner scroll containers</span></label>
```
with:
```html
<label class="toggle"><input id="detectInnerScroller" type="checkbox"><span>Auto-expand scrollable content sections<small>Temporarily removes internal scrollbars on tall content panes during capture so their full content is included, not just what fits in the small scrollable box.</small></span></label>
```

### 3. `options.css` — small touch-up so the new two-line label stacks correctly

Today only `.row span, .stack span` get `display:grid; gap:4px` (line 10)
to stack `<strong>`+`<small>` on separate lines; `.toggle` has never had a
`<small>` before. Extend line 10's selector to include `.toggle span`, and
change `.toggle`'s `align-items: center` (line 12) to `align-items:
flex-start` — this only visibly affects this one toggle (the other three
`.toggle` rows have single-line spans, so `flex-start` vs `center` renders
identically for them).

### Edge cases / known limitations (documented, not solved)

- **Virtualized/windowed lists** (react-window, etc.) only render DOM rows
  near the viewport; CSS expansion can't reveal content never rendered.
  `scrollHeight` may reflect a tall spacer even though rows are absent —
  out of scope, would require simulating real scroll/IntersectionObserver
  events.
- **Infinite-scroll lazy loading** won't trigger, since only CSS changes —
  no scroll events are dispatched. Only content already in the DOM at
  prepare-time is captured.
- **Off-canvas drawers/menus** using `transform` (not
  `display:none`/`visibility:hidden`) that are tall with `overflow-y:auto`
  could be incorrectly expanded now that the visibility gate is dropped.
  Small, accepted risk in exchange for correctly handling below-the-fold
  scrollers; not fixed now.
- **Fixed-size grid tracks**: an expanded grid item nested in a
  non-qualifying (`overflow:hidden`) ancestor with a fixed track size could
  still get clipped by that ancestor. Matches today's existing scope (the
  feature has only ever addressed `auto`/`scroll`/`overlay` containers) —
  not a regression.

## Verification

Manual, via `chrome://extensions` → reload unpacked → real pages:
1. Sidebar-nav (tall, `overflow-y:auto`) + normal main content: full nav list appears, not just the visible portion, and header/footer/main content are also present.
2. Scrollable main content pane + normal sidebar/header/footer (the original bug): full main-panel content captured *and* surrounding chrome captured.
3. Both a scrollable sidebar *and* a scrollable main content pane on one page: both expand.
4. Horizontal-only carousel (`overflow-x:auto`, normal `scrollHeight`): confirm it is **not** expanded — same clipped/scrollable appearance as live browsing.
5. Page with no qualifying inner scrollers: capture is behaviorally identical to before this change (regression check).
6. A capture tall enough after unrolling to trigger existing multi-part splitting (`maxMegapixelsPerPart`/`maxPartWidth`/`maxPartHeight`): confirm splitting still works against the new, taller `contentHeight`.
7. `detectInnerScroller` toggled off in Options: confirm no expansion happens at all.
8. A flexbox-column scrollable panel (`flex: 1 1 Npx` + `overflow-y:auto`) and a CSS-grid scrollable panel: both expand to full content height without being re-clipped by parent flex/grid sizing.
9. A panel whose `overflow-y`/`height` has a CSS `transition`: confirm no partial/mid-animation frame is captured, regardless of `pauseAnimations`.
10. After a capture completes, inspect the live page's DOM (devtools) to confirm every expanded element's inline styles are restored exactly — including elements that had no inline value for a property originally (property should be absent, not present-but-empty).
